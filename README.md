# 历史档案混合编码归一与索引保形

面向一线复核人员的单服务数据工作台。样例数据随仓库提供，结论保留行号、原因码和原值。

## 业务模块

- M1 文件采信：`/api/intake/run`
- M2 编码判定：`/api/encoding/detect`
- M2 编码复核：`/api/encoding/review/*`（按文件留痕、版本对账、可续跑发布）
- M3 字段保形：`/api/fields/normalize`
- M4 内容归一：`/api/content/normalize`
- M5 索引对账：`/api/reconcile`
- M6 批次导出：`/api/export/evidence.csv`

## 核心规则

候选解码必须完整且无替换字符；档号、盒号与超大流水号始终按字符串逐字保留。

## 编码复核（M2 扩展）

同一字节可能被两种编码完整解读，历史评分在平分时偏向 `utf-8-sig` 会选错。
复核工作台在不重写历史的前提下处理这一冲突：

- **按文件复核并记录理由**：原字节（hex）、物理行号、档号前导零逐字保留；理由必填，
  原因码限 `REVIEW_CORRECTED` / `REVIEW_CONFIRMED`。
- **决定只追加、分版本对账**：旧批次档号与差异证据按原解码冻结在索引 v0 基线，
  人工复核从 v1 起追加；`/api/encoding/review/reconcile` 逐文件对照新旧档号与编码。
- **乐观并发**：提交携带 `base_version`，两人并发更正时过期的一方收到 422 `STALE_VERSION`，
  不产生新版本；完全相同的重试幂等返回原版本。
- **索引切换安全**：发布按已存决定逐文件原子切换，单文件冲突整体回滚并保留旧版；
  发布运行由目标摘要派生稳定 `run_id`，中断后按同一 `run_id` 续跑，重试不重复生成版本。
- 页面 `/encoding` 可对照候选解码、版本历史与当前对账结果。

## 启动

```bash
docker compose up --build
```

浏览器访问 `http://localhost:18210`。运行测试：

```bash
docker compose exec -T app pytest -q
```

## 样例流程

依次运行六个模块；最后在批次页复核输入、有效、隔离与输出合计。同一输入摘要重复执行时复用原 `run_id`。
编码页可先「载入演示文件并建立旧批次基线」，再逐文件复核、发布并查看新旧版本对账。

## 已知不覆盖

不处理加密文件与需要外部密钥的对象；不连接真实生产存储。
